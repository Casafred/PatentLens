# 11 - 专利分享功能设计与开发计划

> 状态：批准后实施
> 更新日期：2026-08-03
> 适用架构：Electron（`electron-main.js` + `preload.js` + `src/web.html`）

## 1. 目标与结论

为 PatentLens 增加「专利分享」功能：用户可以把 Google Patents（以下简称 GP）查询结果、已有审查档案/OCR 内容、本地 PDF，以及 Excel/CSV 中的结构化信息，汇集为一个**可追溯、可编辑、可模块化配置**的专利分享项目，并导出为离线可打开的 HTML 文件。

该功能面向研发、产品、管理和知识产权协作中的技术沟通，不以生成法律意见、侵权结论或有效性结论为目标。所有 AI 生成内容都必须带有生成标识，并可回到输入来源核验。

PowerPatent 的有效模式是「统一专利记录 → 必要/扩展板块 → 全局预设与逐篇覆盖 → 预览 → 自包含 HTML 导出」。PatentLens 应采纳该产品思路，但必须复用当前 Electron 架构和已有 GP、审查档案、OCR、AI 与缓存能力；**不得为该功能新增或扩展 Tauri 实现**。

## 2. 方案复核后的关键决策

| 议题 | 决策 | 原因 |
|---|---|---|
| 实时数据与分享内容 | 导入时生成不可变的项目快照；用户可显式刷新来源 | 避免导出内容随缓存、网页或远端数据悄然变化 |
| 字段冲突 | 保留来源、时间与置信度；冲突必须在 UI 中确认 | Excel、GP、PDF OCR 的可靠性和用途不同 |
| AI 的位置 | AI 是可选的模块生成器，不能阻塞基础分享导出 | 用户应能先分享真实原始数据和人工结论 |
| PDF | 默认不嵌入原文；作为明确选择的高级导出选项 | 控制体积、版权风险和敏感内容外发风险 |
| 自定义能力 | 仅支持安全的富文本、字段卡片和数据表，不执行用户 HTML/JS | 导出 HTML 必须可安全地离线打开 |
| 多专利 | 数据模型从第一版支持多篇；第一版先完成单篇与轻量多篇目录 | 避免把对比 AI、附图和大体积资源阻塞基本闭环 |
| 旧 renderer 的耦合 | 只允许一个 facade 读取现有全局状态；分享领域模型不得依赖旧对象形状 | `web-app.js` 已冻结，且现有状态不应扩散成新功能 API |

## 3. 用户工作流

```text
新建分享项目
  → 添加来源（GP / 已有审查档案 / PDF / Excel）
  → 自动规范化、字段映射和冲突确认
  → 编辑项目与专利基础信息
  → 选择模式、预设和模块；可逐篇覆盖
  → 可选生成 AI 研发解读模块
  → iframe 离线预览
  → 导出单文件 HTML
```

### 3.1 输入来源

1. **GP 与 PatentLens 当前查询结果**
   - 导入当前打开的专利原文、当前批量查询缓存，或在分享界面中输入专利号后查询。
   - 可复用字段包括题名、摘要、权利要求、说明书、申请人、发明人、日期、分类、同族、引证与公开链接。
   - 应记录检索日期、数据源标识、原始专利号和公开链接。

2. **已有审查档案与 OCR 内容**
   - 从现有缓存导入案卷基本信息、时间线、文档列表、已完成的 OCR 结果、溯源索引和 AI 审查报告。
   - 分享项目只复制用户选择的文档/分析快照，不与 `kanbanState` 保持双向绑定。

3. **用户上传 PDF**
   - 本地 PDF 先尝试文本层提取；文本量不足时再调用现有 PaddleOCR-VL 或 GLM OCR 管道。
   - OCR 结果统一保存为 Markdown、纯文本、版面块、页码和坐标；这使研发模块可以显示可核验摘录。
   - PDF 与专利的关联顺序为：用户显式指定的专利号 → Excel 映射字段 → 文件名解析建议 → 用户手工确认。不得仅凭 OCR 猜测自动合并。

4. **Excel / CSV**
   - 支持 `.xlsx`、`.xls`、`.csv`；允许选择工作表和标题行。
   - 自动识别中英文常见列名，再由用户确认或更正映射。
   - 未映射列不得丢弃，可作为项目级或专利级自定义字段纳入分享。
   - 一行对应一篇专利；重复行要显示去重/合并策略，不可默默覆盖。

### 3.2 字段合并和可追溯性

每个值都使用如下语义保存，而不是把来源对象直接散落在 UI 中：

```js
{
  value: "...",
  source: "manual | excel | google_patents | dossier | pdf_text | ocr",
  sourceRef: "可公开的来源标识或列名",
  capturedAt: "2026-08-03T...Z",
  confidence: "high | medium | low",
  reviewState: "accepted | conflict | pending"
}
```

默认优先级为：`manual > excel > google_patents > dossier > pdf_text > ocr`。但审查时间线、文档列表等档案专属字段由 dossier 提供，不参与与 GP 的无意义竞争。任何两个非空候选值不同都必须进入冲突列表，由用户选择或保留多个值。

## 4. 模块体系

所有模块均采用 `full / lite / off` 三档。`full` 展示完整的可分享内容，`lite` 仅展示摘要、关键数据或前若干项，`off` 不进入输出。必要模块在数据不足时显示“该来源未提供”而不是编造内容。

### 4.1 必要模块

| ID | 模块 | 内容 |
|---|---|---|
| S1 | 分享封面与目录 | 项目主题、范围、生成时间、专利目录、阅读导航 |
| S2 | 专利基础信息 | 号码、题名、申请人、发明人、关键日期、IPC/CPC、来源 |
| S3 | 技术概要 | 摘要、人工编辑的一句话结论；可选 AI 的问题-手段-效果结构 |
| S4 | 保护范围 | 独立权利要求优先、关键限定词、人工注释；来源不足时明确标示 |
| S5 | 来源与使用说明 | 数据来源、检索日期、AI 标识、版权/保密提示、非法律意见声明 |

### 4.2 适合研发分享的扩展模块

| ID | 模块 | 对研发协作的价值 | 主要输入 |
|---|---|---|---|
| R1 | 技术问题-方案-效果 | 快速理解发明解决什么、如何解决、带来何种效果 | 摘要、权利要求、人工/AI 结论 |
| R2 | 技术要素与系统结构 | 提炼部件、步骤、输入输出和关键接口 | 权利要求、说明书、附图 |
| R3 | 关键参数与边界条件 | 汇集数值范围、材料、工艺、性能指标及适用条件 | 权利要求、实施例、Excel |
| R4 | 实施例与验证证据 | 归纳实施方式、对比实验、测试条件和结果 | 说明书、PDF OCR、Excel |
| R5 | 技术路线差异 | 对多篇专利按技术路线、关键要素、效果做矩阵对比 | 多篇记录、人工/AI 分析 |
| R6 | 研发启发与待验证问题 | 将人工问题、假设、检索空白和后续实验项集中管理 | 用户编辑；AI 仅可给出建议 |
| R7 | 附图与原文摘录 | 展示关键图、OCR 摘录、页码和坐标来源 | PDF、OCR blocks、标注 |
| R8 | 审查与引证背景 | 在需要时展示审查关键节点、引用文献及已有审查报告 | dossier、GP、AI 审查报告 |
| R9 | 同族与地域布局 | 为研发和产品团队展示重点国家、状态和申请节奏 | GP、dossier、Excel |

R6 的表述必须保持为“研发建议/待验证问题”，不能输出“可以规避”“不侵权”“无效”等结论性法律语言。法律判断必须由合格专业人员另行审查。

### 4.3 自定义模块

自定义模块仅支持以下三种渲染器：

- **富文本结论**：用户编辑 Markdown，导出前经过白名单净化。
- **字段卡片**：选择一组标准或 Excel 自定义字段，以卡片或时间线呈现。
- **数据表**：选择列、排序、过滤和显示名称，适合参数或实验数据。

自定义模块不得接收可执行 JavaScript、事件属性、远端脚本 URL 或未经净化的 HTML。模块配置应只保存声明式 JSON，不保存 DOM 节点或函数。

## 5. 技术设计与集成位置

### 5.1 前端模块边界

新实现放在 `src/scripts/app/share/`，建议起步文件如下：

```text
src/scripts/app/share/
  share-entry.js             # 初始化、生命周期和 UI 入口
  share-project-store.js     # 项目快照、IndexedDB 持久化
  share-source-adapters.js   # GP / dossier / PDF / Excel 的领域适配器
  share-field-merge.js       # 规范化、冲突和来源留痕（纯函数）
  share-module-registry.js   # 模块定义、预设、全局/逐篇覆盖
  share-ai.js                # 可选 AI 模块生成与引用校验
  share-renderer.js          # 安全 HTML 模板、预览和导出模型
  share-ui.js                # 向导、映射、配置和预览事件
```

在 `src/web.html` 中增加分享模式入口、页面容器、样式引用和模块脚本；脚本必须在 `web-app.js` 之后加载。分享代码只可通过一个 facade 读取当前 GP/档案缓存，其他分享模块不得直接依赖 `currentData`、`kanbanState`、`GPCache` 或 `_pdPatentCache` 的内部形状。

### 5.2 Electron 能力

| 能力 | 集成方式 |
|---|---|
| 本地 PDF OCR | `electron-main.js` 新增只监听 loopback 的 `POST /api/share/ocr`，复用现有 OCR 函数；请求仅接收受限大小的 Base64 与引擎选项 |
| HTML 保存 | 在 `preload.js` 暴露最小化 `saveShareHtml` bridge，由主进程显示保存对话框后写入文件 |
| Excel 读取 | renderer 读取用户选择的文件内容；使用锁定版本的 SheetJS 浏览器资源，不暴露任意文件系统能力 |
| 历史数据导入 | 在 `share-source-adapters.js` 的 facade 内读取现有缓存快照，复制后断开引用 |

`/api/share/ocr` 不得复用 `/api/gd/extract-text/...` 的 URL 语义，因为后者代表远端案卷文档获取流程。新端点不得落盘保存用户 PDF，除非后续获得明确的项目持久化需求和用户授权。

### 5.3 项目存储

分享项目使用独立 IndexedDB 数据库/对象仓库，与现有 `PatentCache` 隔离。持久化内容应是：项目元数据、已规范化的专利记录、已确认字段、模块配置、OCR 结果和 AI 输出；默认不持久化原始 PDF Base64。导入已有 PatentLens 缓存只能是只读复制。

## 6. 输出 HTML 规格

输出必须为离线可打开的单一 `.html` 文件：

- CSS、交互脚本和项目 JSON 内联；不得依赖 CDN、在线字体、外部 JavaScript 或实时 API。
- 内部目录、折叠模块、全文搜索、打印样式和来源展开可离线工作。
- URL 仅保留经过协议校验的 `https:` 链接；用户可选择是否保留原文外链。
- HTML 内不得含 API Key、Token、Cookie、代理地址、绝对本机路径或未选择的原始文件内容。
- 默认输出轻量版本。嵌入 PDF 必须单独勾选、显示预计大小并设置上限；超过上限应提示使用外链或分开分享。
- 将可展示内容先按字段转义；AI Markdown 采用白名单净化；内嵌 JSON 必须转义 `<`、`>`、`&` 和 Unicode 行分隔符，防止闭合 script 标签注入。

## 7. 分期实施

### 第一阶段：可用闭环

1. 分享项目数据模型、模块注册表、预设与独立持久化。
2. GP/当前缓存导入、Excel/CSV 映射、PDF OCR 上传。
3. 基础必要模块、R1/R3/R7 的非 AI 版本、单篇和轻量多篇目录。
4. iframe 预览、离线 HTML 导出、来源和冲突确认。

### 第二阶段：研发深度协作

1. R2/R4/R5/R6/R8/R9，按需复用已有 OCR、审查报告和溯源数据。
2. 逐篇模块覆盖、关键专利、多人可交换的批注数据。
3. AI 模块生成、重跑、引用有效性检查和人工审核状态。

### 第三阶段：高保真材料

1. 附图标注与原文位置联动。
2. 用户明确授权时的嵌入 PDF 导出。
3. 打印版式、模板主题和大型项目性能优化。

## 8. 验收标准

- 三种输入路径均可生成同一 `PatentRecord`，并可在无网络时预览和导出。
- Excel 的自动映射、手工映射、未映射字段保留和重复专利冲突均有测试。
- PDF OCR 可取消、可失败回退，且不会写入永久临时文件。
- 导出 HTML 不包含密钥、Cookie、本机路径、未经选择的 PDF，且在 Chrome/Edge 离线打开正常。
- AI 输出必须有模型/生成时间标识；引用模块只允许指向存在的来源块。
- 多篇输出在 1、5、10 篇样本下验证体积、预览和导航；大资源有明确提示。
- 所有实现遵守 `docs/12-专利分享开发规范.md`、根目录 `AGENTS.md` 和 `docs/web-app-new-code-policy.md`。

## 9. 界面、入口与后续扩展规划

### 9.1 顶层入口分层

现有「审查文档 / 专利原文 / 智能抽取 / 智能比对」属于查询或单任务模式，继续把复杂的项目式功能塞入 `searchMode` 会让冻结的旧 renderer 承担新的状态分发责任。因此顶层交互划分为两层：

| 层级 | 职责 | 当前实现 |
|---|---|---|
| 快速检索层 | 围绕一个输入框完成即时查询或轻量任务 | 保持现有搜索模式，不扩展 `searchMode` |
| 工作台层 | 管理项目、多个输入来源、多步骤配置、预览与输出 | 独立「分享工作台」入口和独立 section |

「分享工作台」入口与搜索模式按钮并列，但不使用 `.search-mode-btn`，不改变 `searchMode`。工作台入口应使用统一的 `data-workspace-id` / `data-workspace-action` 约定；未来的报告、监测、协作或批量治理工具可以注册为新的工作台，而无需修改已有查询模式。

### 9.2 分享工作台信息架构

```text
分享工作台
├── 项目概览       项目名称、范围、专利数量、待处理事项
├── 材料来源       GP/档案/PDF/Excel 导入、字段冲突、来源状态
├── 数据审核       每篇专利的基础字段、人工修订、来源追溯
├── 分享模块       模板、预设、全局配置、逐篇覆盖、自定义模块
├── 研发洞察       可选 AI 生成、待验证问题、参数/技术路线比较
├── 预览           隔离 iframe 中的离线输出预览
└── 导出           HTML、资源策略、体积、敏感信息扫描与保存
```

首个实现切片只启用「项目概览 / 材料来源」：可以新建空项目，加入当前 PatentLens 原文查询快照，查看已加入专利。其他导航项保持为明确的待建设边界，不伪造完成状态。

### 9.3 可扩展的界面规则

1. **项目条始终可见**：显示项目名称、专利数、保存状态和关闭/返回按钮，避免用户在多步骤操作中丢失上下文。
2. **左侧导航按领域对象而不是技术实现分组**：来源、数据、模块、洞察、预览、导出是稳定的用户心智模型；新增功能优先落入既有区域。
3. **上下文操作放在主视图标题右侧**：例如“加入当前专利”“导入文件”“运行模块”“导出”，避免在顶层堆积按钮。
4. **扩展通过注册表而非条件分支接入**：每个未来工作台或分享子视图应声明 `id`、`label`、`order`、`availability`、`render`，壳层只负责导航和生命周期。
5. **状态隔离**：工作台持有自己的项目草稿；打开或关闭工作台不能修改当前 dossier/GP 结果。需要导入时只复制快照。
6. **渐进披露**：没有专利时优先引导添加来源；有专利后才强调模块、洞察和导出。不可用功能必须说明前置条件。

### 9.4 后续功能的接入路径

| 后续能力 | 推荐入口 | 新增内容 | 不应修改的位置 |
|---|---|---|---|
| PDF/Excel 导入 | 材料来源 | 来源适配器、映射对话框、OCR 任务卡 | `web-app.js` |
| 字段审核和冲突处理 | 数据审核 | 字段比较表、来源抽屉、人工修订 | 旧 GP 详情渲染器 |
| 模板与模块预设 | 分享模块 | 模块注册表、配置面板、逐篇覆盖 | `searchMode` |
| 研发维度 AI 解读 | 研发洞察 | AI 任务、来源引用、审核状态 | 已有审查报告状态 |
| HTML 预览与导出 | 预览/导出 | 安全渲染器、保存 bridge、扫描结果 | 旧 Word/CSV 导出流程 |

该界面壳层是后续功能的稳定契约：只要领域模块符合注册和状态隔离规则，即可增加视图而不改变入口、搜索逻辑或既有检索界面。
